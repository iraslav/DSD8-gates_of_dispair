# DSD-8 processor with an int8 neural-network accelerator

DSD-8 is an 8-bit Harvard-architecture processor written in synthesizable Verilog. The repository includes its assembler, Python reference simulator, self-checking RTL testbenches, trace-based conformance flow, and an int8 neural-network accelerator connected through the processor's I/O bus.

The accelerator implements signed multiply-accumulate (MAC), zero skipping, 24-bit accumulation, power-of-two requantization, and LUT activation. The included 4-6-3 network classifies quantized Iris samples and writes the predicted class (`0`, `1`, or `2`) to the LED output.

A second, coexisting workload — a 4-class CNN driven through a sim-only streaming peripheral — runs on the same unmodified CPU/accelerator hardware; see [CNN multi-class extension](#cnn-multi-class-extension-cnn).

## Architecture at a glance

```text
                 512 x 16 instruction memory
                             |
                             v
  9-bit PC --> decoder --> control FSM --> 8 x 8 register file
                 |                |                 |
                 |                v                 v
                 |           retire trace       8-bit ALU
                 |                                  |
                 +----------> 256 x 8 data memory <-+
                                |
                                v
                       request/ready I/O bus
                    /          |             \
          switches/LEDs   UART/timer/echo   int8 NN accelerator
                                               |
                                    3-stage MAC + requant + LUT
```

Processor resources:

| Resource                  | Size                           |
| ------------------------- | ------------------------------:|
| General-purpose registers | 8 x 8-bit (`R0`-`R7`)          |
| Instruction memory        | 512 x 16-bit                   |
| Program counter           | 9-bit                          |
| Data memory               | 256 x 8-bit                    |
| ALU datapath              | 8-bit                          |
| NN accumulator            | signed 24-bit, wrapping        |
| Control states            | 6 (`FETCH` through `HALTED_S`) |

## Requirements

- Python 3
- Icarus Verilog (`iverilog` and `vvp`) for RTL simulation
- Verilator for `make lint`
- GTKWave for viewing the generated VCD waveform
- NumPy only when retraining or requantizing the models

On Debian/Ubuntu, the tools are typically installed with:

```bash
sudo apt install python3 python3-numpy iverilog verilator gtkwave
```

The generated LUTs, quantized model data, and CNN stream are included, so retraining is not required to run the normal verification flow. Generated benchmark programs, `build/` output, the MNIST cache, and Python caches are not tracked in git: `make bench` and `make cnnbench` regenerate their programs automatically, and `cnn/train_cnn.py` downloads MNIST once (into `cnn/data/mnist/`) only when intentionally retraining.

## Program the processor

Programs are written in DSD-8 assembly and assembled into `$readmemh`-compatible 16-bit instruction images.

Example `demo.asm`:

```asm
        LDI  R1, 0x5B
        OUT  0x02, R1       ; LEDs = 0x5B
        HLT
```

Assemble and run it in the reference simulator:

```bash
mkdir -p build/demo
python3 tools/dsd8asm.py demo.asm \
    -o build/demo/demo.hex \
    --listing build/demo/demo.lst
python3 tools/dsd8sim.py build/demo/demo.hex \
    --trace build/demo/gold.trace \
    --state-out build/demo/state.json
cat build/demo/state.json
```

The JSON state reports registers, flags, the instruction count, data-memory changes, and board outputs such as `leds`.

To execute the same image on the RTL and compare traces directly:

```bash
iverilog -g2005 -s tb_dsd8 -o build/demo/tb.vvp \
    '-Ptb_dsd8.TRACE_FILE="build/demo/dut.trace"' \
    rtl/*.v sim/peripherals.v tb/tb_dsd8.v
vvp build/demo/tb.vvp "+IMEM=$(pwd)/build/demo/demo.hex"
diff -s build/demo/gold.trace build/demo/dut.trace
```

Alternatively, place a program under `tests/conformance/` and run:

```bash
python3 scripts/run_conformance.py <part-of-program-name>
```

Use `tools/dsd8sim_nn.py` instead of `tools/dsd8sim.py` when a program accesses the NN ports, and `tools/dsd8sim_cnn.py` when it also reads the CNN stream ports.

## ISA summary

| Opcode      | Assembly                                | Meaning                       |
| -----------:| --------------------------------------- | ----------------------------- |
| `0x0`       | `NOP`                                   | no operation                  |
| `0x1`       | `LDI Rd, imm8`                          | load an 8-bit immediate       |
| `0x2`       | `LD Rd, [Rp]`                           | load byte from data memory    |
| `0x3`       | `ST [Rp], Rs`                           | store byte to data memory     |
| `0x4`-`0x8` | `ADD/SUB/AND/OR/XOR Rd, Rs1, Rs2`       | ALU operation                 |
| `0x9`-`0xA` | `SHL/SHR Rd, Rs1`                       | logical shift                 |
| `0xB`       | `CMP Rs1, Rs2`                          | set flags from subtraction    |
| `0xC`       | `JMP addr9`                             | absolute jump                 |
| `0xD`       | `BEQ/BNE/BCS/BCC/BMI/BPL/BVS/BVC addr9` | conditional absolute branch   |
| `0xE`       | `IN Rd, port` / `OUT port, Rs`          | I/O transaction               |
| `0xF`       | `HLT`                                   | enter the sticky halted state |

`MOV` and `NOT` are assembler pseudo-instructions implemented with `OR` and `XOR`. Immediates must be written as unsigned values from 0 to 255; encode a negative int8 value with its two's-complement byte (for example, `-2` is `0xFE`). Flags are always ordered `Z N C V`.

## I/O map

| Port          | Access | Function                                                |
| -------------:|:------:| ------------------------------------------------------- |
| `0x00`        | R      | switches                                                |
| `0x01`        | R      | buttons in bits `[4:0]`                                 |
| `0x02`        | W      | LEDs                                                    |
| `0x10`        | W      | seven-segment value                                     |
| `0x11`        | W      | seven-segment enable                                    |
| `0x20`        | W      | simulated UART TX                                       |
| `0x21`        | R      | simulated UART RX (always empty in the reference model) |
| `0x22`        | R      | simulated UART status                                   |
| `0x30`        | R      | simulated timer count                                   |
| `0x31`        | W      | simulated timer control                                 |
| `0x40`        | R/W    | deterministic delayed echo peripheral                   |
| `0x44`        | W      | CNN stream: skip to next sample boundary (sim only)     |
| `0x45`        | R      | CNN stream: next image-phase byte (sim only)            |
| `0x46`        | R      | CNN stream: next weight-phase byte (sim only)           |
| `0x50`-`0x5F` | R/W    | NN accelerator                                          |

All other nonlocal ports are forwarded to the peripheral interface. In the provided simulation model they complete immediately, return zero on reads, and discard writes. The `0x44`-`0x46` ports exist only in `sim/cnn_periph.v` (see the CNN section below).

The bus contract is request/ready based. An access takes effect only when a request (`io_rd` or `io_wr`) and `io_ready` are both high. `io_ready` must remain low while no request is active.

## NN accelerator

The accelerator is locked after reset. Software must write `0xA5` to `NN_KEY` before any other accelerator write has an effect.

| Port          | Name         | Access | Function                                          |
| -------------:| ------------ |:------:| ------------------------------------------------- |
| `0x50`        | `NN_A`       | W      | latch signed int8 activation operand              |
| `0x51`        | `NN_W`       | W      | latch signed int8 weight and trigger one MAC      |
| `0x52`        | `NN_CTRL`    | W      | bit 0 clears accumulator; bit 1 clears counters   |
| `0x53`-`0x55` | `NN_ACC0-2`  | R      | accumulator low/middle/high bytes                 |
| `0x56`        | `NN_SHIFT`   | W      | requantization right shift (`0`-`15`)             |
| `0x57`        | `NN_QOUT`    | R      | `sat8(acc >>> shift)`                             |
| `0x58`        | `NN_LUT_SEL` | W      | LUT bank (`0`-`3`)                                |
| `0x59`        | `NN_ACT`     | R      | activated requantized accumulator                 |
| `0x5A`        | `NN_LUT_IDX` | W      | direct LUT index                                  |
| `0x5B`        | `NN_LUT_VAL` | R      | direct LUT result                                 |
| `0x5C`        | `NN_SKIPCNT` | R      | zero-skipped operation count, saturating          |
| `0x5D`        | `NN_MACCNT`  | R      | executed MAC count, saturating                    |
| `0x5E`        | reserved     | -      | reads zero; writes ignored                        |
| `0x5F`        | `NN_KEY`     | R/W    | write `0xA5` to unlock; read busy/unlocked status |

LUT banks are: `0` ReLU, `1` sigmoid, `2` offset-binary identity, and `3` tanh. `NN_POSTED` selects blocking (`0`) or posted (`1`) MAC-write behavior; dependent reads remain hazard-safe. Both CNN benchmarks were verified under `NN_POSTED = 0` and `NN_POSTED = 1`.

## GTKWave demonstration

```bash
make waveform
gtkwave build/waveform/dsd8_wave.vcd
```

The 11-instruction program in `sim/waveform_demo.asm` unlocks the accelerator, clears it, computes `3 * 4`, reads the accumulator, writes `0x0C` to the LEDs, and halts. `sim/tb_waveform.v` checks the result before finishing.

Only presentation-relevant signals are dumped. GTKWave sees the tidy hierarchy:

```text
tb_waveform.probe.sys   clock, reset, halt, LEDs
tb_waveform.probe.cpu   PC/instruction, state, retire, register write, flags
tb_waveform.probe.io    request/ready, port, read data, write data
tb_waveform.probe.nn    unlock, MAC start/busy, pipe valid, product, accumulator,
                        executed/zero-skipped counters
```

The script also validates the VCD hierarchy so duplicate scopes or duplicate signals fail the run instead of producing a confusing waveform.

## FPGA status

`rtl/dsd8_top.v` exposes `clk`, active-low reset, switches, buttons, LEDs, seven-segment outputs, and `halted`, and is the lint/synthesis top. This repository does **not** include a board-specific constraint file, PLL/clock wrapper, FPGA project, or programming script. `sim/peripherals.v` and `sim/cnn_periph.v` are behavioral simulation code and are not instantiated by `dsd8_top`; the current top ties the external peripheral response to immediate-ready/zero-data behavior.

To run on physical hardware, add the selected board's constraints and clocking, choose how `program.hex` initializes instruction memory in that toolchain, and add a board wrapper or modify the top if physical external peripherals are needed.

## Working rules

- Keep `tb/tb_dsd8.v` unchanged; it is the black-box conformance harness.
- Keep `rtl/` and `tb/` unchanged for CNN work; the CNN extension must stay RTL-neutral.
- Run `make all` after CPU, ISA, memory, or bus changes.
- Run `make bench` after accelerator, LUT, quantization, or generated-program changes.
- Run `make cnnbench` after CNN model, stream, or generator changes.
- Mirror architectural changes in RTL, the golden simulators (`dsd8sim`, `dsd8sim_nn`, `dsd8sim_cnn`), the bit-exact references (`nn_ref`, `cnn_ref`), and the relevant testbenches.
- Install the local pre-push checks with `./scripts/install_hooks.sh` if desired.
- Hosted CI is configured in `.github/workflows/`: `ci.yml` runs lint, unit tests, and conformance on pushes/PRs (conformance is informational on ordinary PRs and authoritative on pushes and tags), and `milestone.yml` runs `make all` on milestone tags. The same checks remain available locally through the Makefile and scripts above; no board files are included.

## CNN multi-class extension (`cnn/`)

A second, coexisting workload runs a tiny 4-class CNN (8x8 image -> conv 3x3 x4 -> ReLU -> 2x2 max-pool -> FC 36x4 -> argmax) on the same unmodified CPU/accelerator/LUT hardware. Each sample's image and weights stream through a sim-only peripheral on ports 0x44-0x46: one sequential pointer, with 0x45/0x46 as two read windows on it and 0x44 (write) skipping to the next sample boundary. Programs consume the stream live, so FC weights are never stored in data memory.

| Artifact                                                                  | What it is                                                                       |
| ------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `cnn/cnn_ref.py`                                                          | bit-exact integer reference (source of truth)                                    |
| `cnn/train_cnn.py` -> `cnn/data/model_float.npz`                          | float model, MNIST digits 0-3 (no sklearn; IDX cached in `cnn/data/mnist/`)      |
| `cnn/quantize_cnn.py` -> `cnn/data/weights_q.json`, `cnn/data/stream.hex` | int8 weights + 64-sample byte stream (float 0.969 / int8 0.969 test accuracy)    |
| `cnn/gen_programs_cnn.py` -> `tests/cnn/`                                 | 64 samples x 4 variants (a0, a2, b0, b1)                                         |
| `sim/cnn_periph.v` + `tools/dsd8sim_cnn.py`                               | stream peripheral + golden simulator with identical pointer semantics            |
| `cnn/tb_cnn_system.v` + `scripts/run_cnn.py`                              | RTL bench: RTL trace == golden trace, 0 protocol errors, LEDs == `cnn_ref` class |

`make cnnbench` regenerates the programs and runs the full 256-run bench; results land in `build/cnn/bench.md`. Program sizes: a0 239, a2 233, b0 388, b1 510 of 512 IMEM words. The stream is 16,128 bytes: 64 samples x 252 bytes (64 image bytes, 4 x 10 convolution weights, and 4 x 37 folded FC weights each), selected with `+CNNSTREAM` and `+CNNSAMP`.

Measured results (64 samples, `build/cnn/bench.md`): a2 mean 57,731 timed cycles and a0 mean 59,387, against 790,545 for shift-and-add software convolution and 1,202,307 for repeated-addition software convolution — 20.8x/13.7x and 20.2x/13.3x speedups. The accelerator variant retires about 24x fewer golden instructions than the repeated-addition baseline (13,696 vs 332,617); the multiply loops dominate the workload, and the MAC pipeline plus zero skipping removes them while the stream peripheral supplies the pointer/handshake traffic. Golden-sim mean instructions per image: a0 14.2k, a2 13.7k vs b1 208.9k, b0 332.6k.

All 64 samples x 4 variants pass on LEDs and are byte-exact on the intermediate conv-pool and logit DMEM (POOL at 128..163, LOG at 168..171) against `cnn/cnn_ref.py`, in both the golden simulator and RTL, under both `NN_POSTED` settings. The MLP flow (`make bench`) is untouched; `make all` stays green (13/13 unit, 2/2 conformance).
